# 补丁版本路线图（0.0.2 – 0.0.5）

0.0.1 是首个可用版本。之后四个版本**全部是补丁版本**，目标只有一个：把已经承诺的能力做稳。

## 版本策略

| 项目 | 约定 |
| --- | --- |
| 版本语义 | 遵循 SemVer：`0.0.x` 只做补丁，`PATCH` 递增 |
| 功能范围 | **不引入新功能**。不新增 Agent、不新增设置项、不改 UI 信息架构 |
| 配置兼容 | **不改配置格式**，`Settings.version` 在整个 0.0.x 保持 `1`；老 `settings.json` 直接可读 |
| 数据兼容 | 不迁移、不重命名 `conversations/`、`kb/`、`memory/` 下的文件结构 |
| 破坏性变更 | 无。任何需要用户改配置的改动一律推迟到 0.1.0 |
| 升级方式 | 应用内 **设置 → 关于 → 检查更新**（`update:check`）检测；检测到后下载新版安装包覆盖安装，数据与设置保留 |

发布节奏与发布物：

| 版本 | 发布日期 | 定位 | 发布物 |
| --- | --- | --- | --- |
| 0.0.2 | ✅ 2026-10-23（已发布） | 安全与测试 | `Run-worker-0.0.2-setup.exe` |
| 0.0.3 | 2026-11-06（预计） | 稳定性与兼容性 | `Run-worker-0.0.3-setup.exe` |
| 0.0.4 | 2026-11-20（预计） | 安全与权限 | `Run-worker-0.0.4-setup.exe` |
| 0.0.5 | 2026-12-04（预计） | 更新通道与安装器 | `Run-worker-0.0.5-setup.exe` |

每个版本同时产出 `latest.yml`（electron-builder 自动生成）并随 Release 一并上传留档。应用内的更新检测走 GitHub Release API 比对版本号，不依赖该文件解析（它是安装包清单，留给后续增量更新使用）。

## 0.0.2 — 安全与测试补丁（✅ 已发布 2026-10-23）

原计划的稳定性清单因安全项提前而并入 0.0.3。本版实际内容：

### 已完成

| # | 问题 | 处理 |
| --- | --- | --- |
| 1 | API Key 明文存储（SECURITY.md「后续小版本评估」项） | Electron `safeStorage`（Windows DPAPI）加密落盘 `enc:v1:` 密文，存量明文启动时自动迁移；系统不支持加密时回退明文并记日志 |
| 2 | 命令判定变体绕过（原 0.0.4 #1 提前） | 归一化已覆盖大小写/多空格；补内置变体模式：`rimraf`、`ri -r`、`find -delete`、`shred`、`wmic delete`、.NET Delete、`\\.\PhysicalDrive`、`git clean -fdx`、`erase /s`、`truncate -s 0` |
| 3 | 更新包无完整性参照（原 0.0.5 签名校验的部分前置） | 更新信息透出安装包 SHA-256（GitHub 资产 digest），设置 → 关于可见 |
| 4 | trace 三态与 ticker 补跑两个测试空白（CONTRIBUTING「已知空白」） | 演示模式与真实路径同构落 trace（C6/C7）；F4 预置到期任务验证 ticker 补跑；平台用例 10 → 14，E2E 22 → 26 |

### 验证方式

- `npm test` 14/14；`npm run test:e2e` 输出 `ALL PASS (26/26)`。
- 手动：填一个 Key 后打开 `%APPDATA%/Run worker/settings.json`，确认 Key 为 `enc:v1:` 密文；重 launch 后渠道测试仍通过。

## 0.0.3 — 稳定性与兼容性补丁

**预计发布 2026-11-06 · 主题：不崩、不卡、不乱码，换个渠道也能用**

### 目标

消除 0.0.1 反馈中最影响日常使用的稳定性问题（原 0.0.2 清单），并让非标准 OpenAI 兼容服务和边界时间计算不再出错。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | 切换会话时上一轮的思考流未中断，增量写入新会话 | `run:thinking` / `run:content` 串台 | `chat:abort` 在切换会话时自动触发；事件按 `runId` 严格过滤 |
| 2 | 中文或含空格路径下 `python.exec` 执行失败（`can't open file`） | 数据分析、模型生成 | 命令行参数统一加引号转义 |
| 3 | 浅色主题下工具卡片文字与背景对比度不足 | 可读性 | 卡片内文本改用语义色变量，按 WCAG AA 校正 |
| 4 | 网络抖动时 `run:end` 缺失，界面永久停在“运行中” | 会话无法继续输入 | 主进程 try/finally 保证必发 `run:end`；渲染侧加超时兜底 |
| 5 | 日志文件跨天不切分，单文件持续膨胀 | 磁盘占用 | 按 `main-YYYY-MM-DD.log` 每日新建 |
| 6 | `0 9 31 * *` 这类日期在部分月份不存在，`nextRunAt` 顺延无提示 | 定时任务 | 任务卡片与日志明确提示“本月无触发日，已顺延到 X 月 X 日” |
| 7 | `/v1/models` 返回结构与标准不一致时，渠道测试误报失败 | 模型渠道 | 兼容 `data[].id` 与 `data[].name` 两种结构，解析失败降级为手填 |
| 8 | `429` 限流时直接失败，不提示是哪个渠道 | 免费模型用户 | 错误信息带上渠道名与建议（等待重试 / 换渠道 / 关免费优先） |
| 9 | Ollama 未启动时请求挂起直到超时 | 本地模型 | 连接超时缩短并给出“请先运行 `ollama serve`”的明确提示 |
| 10 | 系统代理开启时访问 `localhost:11434` 被代理拦截 | 本地模型 | 本地地址加入 no-proxy 判断 |
| 11 | 导出 Markdown 时思考内容里的 `</details>` 破坏折叠结构 | 导出 | 导出前对思考内容做标签转义 |
| 12 | 会话索引在异常退出后残留不存在的会话条目 | 侧边栏 | 启动时校验索引与文件一致性，孤儿条目自动剔除 |

### 验证方式

- 构造 cron 边界用例：`0 9 31 * *`、`0 0 29 2 *`，连续推进 12 个月，确认 `nextRunAt` 与实际触发日期一致，且无触发日时有提示。
- 用假的 `/v1/models` 响应（缺字段、包一层 `result`）跑渠道测试。
- 断开 Ollama 后发起对话，确认 15 秒内给出可读错误。
- `npm test` 覆盖 cron 计算与 Markdown 导出用例。

### 升级方式

同 0.0.2。若使用自定义渠道，升级后建议在设置里点一次“测试连接”刷新 `status`。

## 0.0.4 — 安全与权限补丁

**预计发布 2026-12-04 · 主题：能动手，但动手前问一句**

### 目标

收紧命令判定的误判与漏判，补齐审批流程中的并发与记忆问题，约束文件写入边界。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | 一轮内多个工具并发请求审批时弹窗互相覆盖 | 审批流程 | 审批队列串行化，逐个弹出；`chat:approve` 按 `requestId` 精确匹配 |
| 2 | “本类别不再询问”选择未生效，同类命令反复弹窗 | 体验 | `remember` 在本轮运行内按工具名记住，运行结束即失效（不写设置） |
| 3 | `fs.write` 可写到工作目录之外（如系统目录） | 文件安全 | 写入路径需在 `agent.workspaceDir`、`artifacts/` 或用户显式选择过的目录内，否则要求审批 |
| 4 | `approvalMode: 'never'` 时黑名单仍生效但无任何提示 | 风险知情 | 启用 `never` 时给出一次显式风险确认 |

> 原 #1（denyPatterns 变体绕过）已提前在 0.0.2 完成。

### 验证方式

- 安全用例集回归：`RM -RF /`、`rimraf`、`find -delete`、`format c:`、`diskpart`、`shutdown /s`，确认全部被拦截或强制审批（用例已在 0.0.2 进 `npm test`）。
- 构造并发：让 Agent 一轮内连续请求两个高风险工具，确认弹窗按序、结果不错配。
- 回归日志脱敏：`logs/main-*.log` 全文搜索 `sk-`、`Bearer`、`apiKey`，应无明文（该能力已在 0.0.1 实现，本题只做回归）。
- `npm test` 增加权限判定用例。

### 升级方式

同 0.0.2。升级后建议打开一次设置 → Agent，确认 `denyPatterns` 仍是默认值（不会被自动改写）。

## 0.0.5 — 更新通道与安装器补丁

**预计发布 2026-12-18 · 主题：升级这件事本身要可靠**

### 目标

把“检查更新 → 下载 → 覆盖安装 → 数据保留”这条链路走通走稳，并完成 Electron 小版本升级以修复上游 Windows 相关问题。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | Electron 33.4.11 在 Windows 11 某些缩放组合下白屏 | 启动 | 升级到 33.x 最新补丁版，回归 `devicePixelRatio` 非整数的多屏场景 |
| 2 | 安装器未校验签名，SmartScreen 频繁拦截 | 安装 | 补齐发布签名，并在安装器说明中写清“未知发布者”的处理路径（安装包 SHA-256 已在 0.0.2 透出，可人工校验） |
| 3 | GitHub 二级限流（secondary rate limit）不返回 `x-ratelimit-remaining`，被误判成「无权访问（HTTP 403）」 | 更新 | 补 `retry-after` 头与响应体 `message` 关键字判断，把二级限流并入「请求过于频繁」档 |
| 4 | 重复安装后 `PATH` 里出现多条相同目录 | 环境变量 | 安装脚本写入前做去重比较（已有 `RWStrContains` 逻辑覆盖，补大小写与尾部反斜杠归一化） |
| 5 | 卸载后 `PATH` 残留空条目（`;;`） | 环境变量 | 重组 `PATH` 时跳过空段 |
| 6 | 更新提示不显示版本差异说明 | 体验 | 提示中展示 `currentVersion → latestVersion` 与 Release notes 摘要 |
| 7 | 手动改过安装目录后，旧目录的 `RUN_WORKER_HOME` 未更新 | 环境变量 | 安装时无条件覆写 `HKCU\Environment\RUN_WORKER_HOME` 并广播刷新 |

### 验证方式

- 在 Windows 11 + 125%/150% 缩放的双屏环境启动，确认无白屏。
- 连续安装两次到同一目录，`echo %PATH%` 中该目录只出现一次。
- 卸载后检查 `HKCU\Environment` 下 `RUN_WORKER_HOME` 已删除、`PATH` 无空条目。
- 用 `v0.0.4` 安装包 + 指向 `0.0.5` 的 Release 验证检测与提示文案。

### 升级方式

这是 0.0.x 系列最后一个补丁版本。从 0.0.5 起，更新提示会同时给出下载链接与版本差异摘要；覆盖安装不会动 `%APPDATA%/Run worker/`。

## 不在补丁范围内

以下需求明确**不属于** 0.0.2 – 0.0.5，请勿以 Bug 形式提交：

- 新增 Agent、新增内置工具、新增模型渠道预设
- 插件市场、多窗口、团队协作
- 设置项增删或字段重命名（会改变 `settings.json` 结构）
- 静默自动替换式更新（无提示下载并安装）

这些需要以小版本（`0.1.0` 起）规划，届时会单独给出迁移说明。
