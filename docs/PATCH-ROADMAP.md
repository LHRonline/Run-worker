# 补丁版本路线图（0.0.2 – 0.0.5）

0.0.1 是首个可用版本。之后四个版本**全部是补丁版本**，目标只有一个：把已经承诺的能力做稳。

## 版本策略

| 项目 | 约定 |
| --- | --- |
| 版本语义 | 遵循 SemVer：`0.0.x` 只做补丁，`PATCH` 递增 |
| 功能范围 | **不引入新功能**。不新增 Agent、不新增设置项、不改 UI 信息架构 |
| 配置兼容 | **不改配置格式**，`Settings.version` 在整个 0.0.x 保持 `1`；老 `settings.json` 直接可读 |
| 数据兼容 | 不迁移、不重命名 `conversations/`、`kb/`、`memory/` 下的文件结构 |
| 破坏性变更 | 无。任何需要用户改配置的改动一律推迟到 0.1.0 |
| 升级方式 | 应用内 **设置 → 关于 → 检查更新**（`update:check`）检测；检测到后下载新版安装包覆盖安装，数据与设置保留 |

发布节奏与发布物：

| 版本 | 预计发布日期 | 定位 | 发布物 |
| --- | --- | --- | --- |
| 0.0.2 | 2026-11-06（预计） | 稳定性 | `Run-worker-0.0.2-setup.exe` |
| 0.0.3 | 2026-11-20（预计） | 兼容性 | `Run-worker-0.0.3-setup.exe` |
| 0.0.4 | 2026-12-04（预计） | 安全与权限 | `Run-worker-0.0.4-setup.exe` |
| 0.0.5 | 2026-12-18（预计） | 更新通道与安装器 | `Run-worker-0.0.5-setup.exe` |

每个版本同时产出 `latest.yml`（electron-builder 自动生成）并随 Release 一并上传留档。应用内的更新检测走 GitHub Release API 比对版本号，不依赖该文件解析（它是安装包清单，留给后续增量更新使用）。

## 0.0.2 — 稳定性补丁

**预计发布 2026-11-06 · 主题：不崩、不卡、不乱码**

### 目标

消除 0.0.1 反馈中最影响日常使用的稳定性问题：流式输出在切换上下文后错乱、中文路径下脚本执行失败、浅色主题下工具卡片不可读。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | 切换会话时上一轮的思考流未中断，增量写入新会话 | `run:thinking` / `run:content` 串台 | `chat:abort` 在切换会话时自动触发；事件按 `runId` 严格过滤，未知 `runId` 直接丢弃 |
| 2 | 中文或含空格路径下 `python.exec` 执行失败（`can't open file`） | 数据分析、模型生成 | 命令行参数统一加引号转义，不再拼接裸路径 |
| 3 | 浅色主题下工具卡片文字与背景对比度不足 | 可读性 | 卡片内文本改用语义色变量，对比度按 WCAG AA 校正 |
| 4 | 网络抖动时 `run:end` 缺失，界面永久停在“运行中” | 会话无法继续输入 | 主进程 try/finally 保证必发 `run:end`；渲染侧加超时兜底 |
| 5 | 长会话保存时偶发半截 JSON | 会话丢失 | 保留原子写，补齐 `rename` 失败分支的临时文件清理 |
| 6 | 日志文件跨天不切分，单文件持续膨胀 | 磁盘占用 | 按 `main-YYYY-MM-DD.log` 每日新建，超期文件不自动删除（可手动清） |
| 7 | 粘贴超长文本时输入框卡顿 | 交互 | 输入框改为非受控 + 防抖统计，长文本不再逐字重渲染 |

### 验证方式

- 手动：开两个会话交替发问，确认思考流不串台；在 `D:\我的项目\测试\` 下跑 Python 脚本。
- 回归：`npm run typecheck`、`npm test` 全绿；`npm run pack` 启动免安装包跑一轮工具调用。
- 观察：连续 30 分钟长对话，检查 `logs/` 是否按天切分，`run:end` 每次都有。

### 升级方式

设置 → 关于 → 检查更新；或直接下载 `Run-worker-0.0.2-setup.exe` 覆盖安装。设置与历史对话保留。

## 0.0.3 — 兼容性补丁

**预计发布 2026-11-20 · 主题：换个渠道也能用**

### 目标

让非标准 OpenAI 兼容服务和边界时间计算不再出错，减少“明明 Key 是对的却报错”的排查成本。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | `0 9 31 * *` 这类日期在部分月份不存在，`nextRunAt` 直接落到下一个有该日期的月份，用户容易误以为任务漏跑 | 定时任务 | 在任务卡片与日志里明确提示“本月无触发日，已顺延到 X 月 X 日”；保持标准 5 段 cron 语义不变 |
| 2 | `/v1/models` 返回结构与标准不一致时，渠道测试误报失败 | 模型渠道 | 兼容 `data[].id` 与 `data[].name` 两种结构，解析失败降级为“连接成功，模型列表需手填” |
| 3 | `429` 限流时直接失败，不提示是哪个渠道 | 免费模型用户 | 错误信息带上渠道名与建议（等待重试 / 换渠道 / 关免费优先） |
| 4 | Ollama 未启动时请求挂起直到超时 | 本地模型 | 连接超时缩短并给出“请先运行 `ollama serve`”的明确提示 |
| 5 | 系统代理开启时访问 `localhost:11434` 被代理拦截 | 本地模型 | 本地地址加入 no-proxy 判断 |
| 6 | 导出 Markdown 时思考内容里的 `</details>` 破坏折叠结构 | 导出 | 导出前对思考内容做标签转义 |
| 7 | 会话索引在异常退出后残留不存在的会话条目 | 侧边栏 | 启动时校验索引与文件一致性，孤儿条目自动剔除 |

### 验证方式

- 构造 cron 边界用例：`0 9 31 * *`、`0 0 29 2 *`，连续推进 12 个月，确认 `nextRunAt` 与实际触发日期一致，且无触发日时有提示。
- 用假的 `/v1/models` 响应（缺字段、包一层 `result`）跑渠道测试。
- 断开 Ollama 后发起对话，确认 15 秒内给出可读错误。
- `npm test` 覆盖 cron 计算与 Markdown 导出用例。

### 升级方式

同 0.0.2。若使用自定义渠道，升级后建议在设置里点一次“测试连接”刷新 `status`。

## 0.0.4 — 安全与权限补丁

**预计发布 2026-12-04 · 主题：能动手，但动手前问一句**

### 目标

收紧命令判定的误判与漏判，补齐审批流程中的并发与记忆问题，约束文件写入边界。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | `denyPatterns` 只做小写包含匹配，`RM -RF`、`rm  -rf`（多空格）绕过 | 命令安全 | 归一化空白后再比对；新增对常见变体（`rm -r -f`、`del /q /s`）的内置模式 |
| 2 | 一轮内多个工具并发请求审批时弹窗互相覆盖 | 审批流程 | 审批队列串行化，逐个弹出；`chat:approve` 按 `requestId` 精确匹配 |
| 3 | “本类别不再询问”选择未生效，同类命令反复弹窗 | 体验 | `remember` 在本轮运行内按工具名记住，运行结束即失效（不写设置） |
| 4 | `fs.write` 可写到工作目录之外（如系统目录） | 文件安全 | 写入路径需在 `agent.workspaceDir`、`artifacts/` 或用户显式选择过的目录内，否则要求审批 |
| 5 | `approvalMode: 'never'` 时黑名单仍生效但无任何提示 | 风险知情 | 启用 `never` 时给出一次显式风险确认 |

### 验证方式

- 安全用例集：`RM -RF /`、`rm   -rf ~`、`format c:`、`diskpart`、`shutdown /s`，确认全部被拦截或强制审批。
- 构造并发：让 Agent 一轮内连续请求两个高风险工具，确认弹窗按序、结果不错配。
- 回归日志脱敏：`logs/main-*.log` 全文搜索 `sk-`、`Bearer`、`apiKey`，应无明文（该能力已在 0.0.1 实现，本题只做回归）。
- `npm test` 增加权限判定用例。

### 升级方式

同 0.0.2。升级后建议打开一次设置 → Agent，确认 `denyPatterns` 仍是默认值（不会被自动改写）。

## 0.0.5 — 更新通道与安装器补丁

**预计发布 2026-12-18 · 主题：升级这件事本身要可靠**

### 目标

把“检查更新 → 下载 → 覆盖安装 → 数据保留”这条链路走通走稳，并完成 Electron 小版本升级以修复上游 Windows 相关问题。

### 修复清单

| # | 问题 | 影响面 | 处理 |
| --- | --- | --- | --- |
| 1 | Electron 33.4.11 在 Windows 11 某些缩放组合下白屏 | 启动 | 升级到 33.x 最新补丁版，回归 `devicePixelRatio` 非整数的多屏场景 |
| 2 | 安装器未校验签名，SmartScreen 频繁拦截 | 安装 | 补齐发布签名，并在安装器说明中写清“未知发布者”的处理路径 |
| 3 | GitHub 二级限流（secondary rate limit）不返回 `x-ratelimit-remaining`，被误判成「无权访问（HTTP 403）」 | 更新 | 补 `retry-after` 头与响应体 `message` 关键字判断，把二级限流并入「请求过于频繁」档 |
| 4 | 重复安装后 `PATH` 里出现多条相同目录 | 环境变量 | 安装脚本写入前做去重比较（已有 `RWStrContains` 逻辑覆盖，补大小写与尾部反斜杠归一化） |
| 5 | 卸载后 `PATH` 残留空条目（`;;`） | 环境变量 | 重组 `PATH` 时跳过空段 |
| 6 | 更新提示不显示版本差异说明 | 体验 | 提示中展示 `currentVersion → latestVersion` 与 Release notes 摘要 |
| 7 | 手动改过安装目录后，旧目录的 `RUN_WORKER_HOME` 未更新 | 环境变量 | 安装时无条件覆写 `HKCU\Environment\RUN_WORKER_HOME` 并广播刷新 |

### 验证方式

- 在 Windows 11 + 125%/150% 缩放的双屏环境启动，确认无白屏。
- 连续安装两次到同一目录，`echo %PATH%` 中该目录只出现一次。
- 卸载后检查 `HKCU\Environment` 下 `RUN_WORKER_HOME` 已删除、`PATH` 无空条目。
- 用 `v0.0.4` 安装包 + 指向 `0.0.5` 的 Release 验证检测与提示文案。

### 升级方式

这是 0.0.x 系列最后一个补丁版本。从 0.0.5 起，更新提示会同时给出下载链接与版本差异摘要；覆盖安装不会动 `%APPDATA%/Run worker/`。

## 不在补丁范围内

以下需求明确**不属于** 0.0.2 – 0.0.5，请勿以 Bug 形式提交：

- 新增 Agent、新增内置工具、新增模型渠道预设
- 插件市场、多窗口、团队协作
- 设置项增删或字段重命名（会改变 `settings.json` 结构）
- 静默自动替换式更新（无提示下载并安装）

这些需要以小版本（`0.1.0` 起）规划，届时会单独给出迁移说明。
